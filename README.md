# Pokémon Box: Ruby & Sapphire decompilation project

This project has an initial, byte-exact DOL split-and-relink baseline for three
Nintendo GameCube releases. It does not yet contain reconstructed source or
confirmed translation-unit boundaries.

## Supported image identities

The supplied disc headers and extracted DOL hashes identify these images:

- `GPXE01` — NTSC-U, revision 1, DOL SHA-1 `99275f11bc36f1e5c9034d317bb2fdceddd2a301`
- `GPXP01` — PAL, revision 1, DOL SHA-1 `cb254692ba45ab2224c5b221c45bfab9a39a08ba`
- `GPXJ01` — NTSC-J, revision 0, DOL SHA-1 `ff1087d5649d7e54509b2e2d6e15e3ff24a8bc62`

Place a legally obtained image in the matching directory under `orig/`:

```text
orig/GPXE01/
orig/GPXP01/
orig/GPXJ01/
```

The supplied images are CISO files. Disc images and generated build output are
ignored by git and must never be committed.

## Build

Requires Python 3 and Ninja. From the repository root, select a version and
build it:

```sh
python3 configure.py --version GPXE01 --no-progress
ninja -j2
```

Replace `GPXE01` with `GPXP01` or `GPXJ01` to build another revision. The first
build downloads decomp-toolkit and linker tools. A passing SHA-1 check means the
relinked `main.dol` is byte-exact. The current generated splits contain only
section boundaries; decomp-toolkit creates autogenerated assembly units for the
relink. This is a build baseline, not a claim of source matching or known
original compiler settings. Compiler flags and linker version in
`configure.py` are dtk-template defaults pending object-level evidence.

`configure.py` and `tools/` derive from the CC0
[dtk-template](https://github.com/encounter/dtk-template) at commit
`95a941f755919ebe50c1725a4ce73524470e7a02`.

The US DOL also has a saved, headless [Ghidra analysis](docs/GHIDRA_ANALYSIS.md)
for function and call-graph research. The dashboard exposes its verified direct
calls as a searchable graph. It does not establish linked matches.

## m2c drafts

The local companion harness can draft C hypotheses from the generated DOL
assembly without adding source files or claiming a match. From the
`Pokemon-Decomp-Harness` root, run:

```sh
python3 harness/box_m2c_drafts.py --version GPXE01 --limit 48 --jobs 4
```

The runner requires a byte-exact DOL build. It checks selected `.fn` addresses
and sizes against `symbols.txt`, saves input assembly and drafts under ignored
`build/decomp-support/<version>/`, and keeps a resumable sweep history for the
Box dashboard. `--version` also accepts `GPXP01` and `GPXJ01`. These drafts
have no verified source types, compiler settings, scratch compile, objdiff
score, or linked match. Do not promote them into `src/` without that evidence.

The first GPXE01 sweep sampled 48 functions across the DOL: 47 produced m2c
output and one was unsupported. Only 10 of the 47 outputs lacked unresolved
field macros; this is a draft-production result, not 47 compilable functions.
Four-function smoke sweeps also produced four outputs each for GPXP01 and
GPXJ01. All sweep records and draft C files remain in ignored build storage.

## Scratch C verification

The first C experiment is in
`research/candidates/OSExceptionHandlers.c`. It adapts
the exception-handler table access from the matched SDK corpus. Compiling it
with GC/1.2.5n and comparing against the generated retail object with objdiff
gives function-level 100% scores for `__OSSetExceptionHandler` (28 bytes) and
`__OSGetExceptionHandler` (20 bytes). They remain outside `src/`: splitting
their text removes the co-located `__OSDBJUMPEND` label needed by
`OSExceptionInit`, so the full link does not yet succeed.

The assembly-only m2c draft for `fn_800FB7F8` compiles to an exact 24-byte
function with GC/1.2.5n and is now linked. To run bounded, review-only model
attempts over the remaining drafts from the harness checkout:

```sh
python3 harness/box_draft_attempts.py --host http://127.0.0.1:18080/v1 --loop --max-attempts 4
```

The model server must already be reachable at that endpoint. Attempt sources,
compiler output, objdiff reports, and resumable `state.json` stay under ignored
`build/decomp-support/GPXE01/attempts/`. Scores are function-level scratch
measurements across the experimentally evidenced GC/1.2.5n, GC/1.3,
GC/1.3.2, GC/2.0, and GC/2.5 profiles, not proof of the original compiler or
a linked source unit.

For a reproducible, RPC-free check of every m2c draft, run from the harness
checkout:

```sh
PYTHONPATH=harness python3 harness/box_validate_drafts.py --version GPXE01
```

The serial validator uses the same byte-field fallback as the Colosseum
scratch validator. It retains per-draft compiler and objdiff artifacts under
ignored `build/decomp-support/GPXE01/validation/` and updates the Box m2c
report. The first full 48-row pass compiled eight drafts and gave four a
function-level 100% scorer result. A scorer result alone is not a linked
match. `fn_80048920` is now linked after its own split and full SHA-1 check.

The project-wide 257-512-byte pass generated 86 drafts from 96 selected
functions. Five compiled, with `fn_8007DB5C` the best at 99.09%; none were
instruction-exact. The pass also exposed a weaker 79.02% m2c reconstruction
of `bitrev`. Its byte-identical cross-project source instead compiled at 100%
with an empty instruction diff and is now linked after a full SHA-1 check.

`research/candidates/OSInitThreadQueue.c` carries the byte-identical SDK
function shared with Colosseum and XD. It scores 100% with GC/1.2.5n against
Box's 16-byte target and has no instruction diff. It is now linked from
`src/dolphin/os/OSInitThreadQueue.c` with a full SHA-1 check.

The whole-DOL conservative leaf sweep checks only direct field accesses,
constant returns, empty leaves, and zero stores. Its current retained result
contains 578 instruction-exact scratch functions. The promotion step rejects
objects with non-text ownership, so `fn_8002E860` remains assembly-backed
because its target object also owns a `.ctors` entry. The other 577 functions
(3,864 bytes) are linked in 264 mechanically grouped source units under
`src/game/leaf_sweep/`.

The byte-identical cross-project corpus has also supplied ten Dolphin SDK
functions, including `__GXSetTmemConfig`, `GXInitTexCacheRegion`,
`GXInitFifoBase`, `UpdateIconOffsets`, `__CARDCheckSum`, and `__CARDVerify`,
plus 18 CRT functions. The CRT set includes the complete five-function
`memmove` implementation as one GC/2.0 translation unit, `modf`, stdio
wrappers, `fwide`, and `round_decimal`. Each candidate was first
instruction-checked in scratch storage, then linked at its retail address and
accepted only after the complete DOL passed its SHA-1 check. Overall GPXE01
progress is now 711 linked functions and 13,776 code bytes (0.94%), with a
byte-exact DOL.

```sh
PYTHONPATH=harness python3 harness/box_leaf_candidates.py --all
PYTHONPATH=harness python3 harness/box_promote_leaves.py
```

The original largest US autogenerated range, `auto_03_8008AB74_text`, contains
406 functions across 219,776 bytes. To generate conservative leaf-function C
and score the remaining functions against active target objects, run from the
harness:

```sh
PYTHONPATH=harness python3 harness/box_leaf_candidates.py --version GPXE01
```

The first pass found 31 instruction-exact scratch hypotheses (224 bytes) from
31 bounded templates. Subsequent exact drafts and corrected argument positions
have brought the original range to 90 linked C functions (3,180 bytes, 1.45%)
across 66 mechanically split subunits. The GPXE01 DOL remains SHA-1 exact.
The current input-checked sweep has no further template matches; records are
retained under ignored `build/decomp-support/GPXE01/leaf-sweeps/` and shown on
the Box m2c dashboard. These splits do not establish original C file
boundaries. See [candidate review](docs/CANDIDATE_REVIEW.md) for the linked
progress audit and remaining mismatches.

## Project rules

These rules mirror the current local Colosseum workflow and the current TeamOrre
XD contribution guidance, adapted for a new project:

- Keep changes small and focused; use a pull request for every contribution.
- Use evidence-backed names from symbol maps when available.
- Do not invent symbols, types, splits, ownership, or compiler settings.
- Keep placeholder splits until the binary and build evidence confirm them.
- Verify split or symbol changes with a successful build before treating them as
  project progress.
- Add source through the project's configure/object declarations and confirmed
  split ownership.
- Keep nonmatching source as a candidate until the generated report proves it
  belongs in the linked build.
- Use objdiff against generated target/source objects before claiming a match.
- Do not commit `.inc` files, extracted game assets, target objects, compiler
  binaries, ROM-derived snippets, asm wrappers, inline assembly, or included
  assembly as decompilation progress.
- Do not edit symbols, splits, linker configuration, or object declarations only
  to improve a metric; every such change needs a build reason.
- Keep local harness experiments and research notes separate from the active
  source tree.
